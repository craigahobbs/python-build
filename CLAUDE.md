# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

python-build is a GNU Make-based build system for Python package development. The makefiles *are* the
product — there is no Python source code here. The deliverables are:

- `Makefile.base` — the build system that downstream Python projects include. Provides the
  `test`, `lint`, `doc`, `cover`, `commit`, `publish`, `changelog`, `gh-pages`, `clean`, and
  `superclean` targets.
- `Makefile.tool` — a lighter variant for non-package tool repositories.
- `pylintrc` — the shared pylint configuration.

Downstream projects download `Makefile.base` and `pylintrc` from GitHub Pages
(`https://craigahobbs.github.io/python-build/...`) at make time, so published changes propagate to
all consumers. README.md is the authoritative user documentation for the targets and variables —
update it when adding or changing them.

## Commands

- `make test` — run all tests
- `make test-<name>` — run a single test, e.g. `make test-commit` (names match `tests/<name>/`
  directories)
- `make commit` — pre-commit target (runs `test`)
- `make changelog` — update CHANGELOG.md via simple-git-changelog
- `make clean` — remove `build/` and `test-actual/`

## Test architecture

Tests are snapshot tests of the *commands make would run*, not of actual execution:

- Each test is a fixture directory `tests/<name>/` containing a small Makefile that sets variables
  (placeholder values like `python:3.X` and `X.Y.*`) and includes `../../Makefile.base` — or
  `../../Makefile.tool` for the `tool-*` tests.
- The `TEST_RULE` function in the top-level `Makefile` runs `make -n` (dry run) in the fixture with
  a given goal and variables, normalizes the make sub-level number in "Nothing to be done" messages
  (`make[2]` → `make[X]`) with sed, writes the output to `test-actual/<name>.txt`, and diffs it
  against `test-expected/<name>.txt`. Nothing is ever executed.
- Fixtures select which code path is snapshotted by checking in empty venv marker files: a
  `build/venv/system.build` marker makes the dry run skip venv creation, so fixtures whose subject
  is not venv creation check one in to keep those commands out of their expected output. Targets
  that use the `-util` venv (`publish`, `changelog`) also need a `build/venv/system-util.build`
  marker, and the `tool-*` fixtures' marker is `build/env.build`. The `-2` fixture variants pair a
  with-marker fixture against a without-marker one to
  cover both paths (e.g. `tests/test/` shows venv creation, `tests/test-2/` does not).
- On failure, the actual output is left at `test-actual/<name>.txt`. If the output change is
  intentional (e.g. after editing `Makefile.base` or bumping a pinned tool version), copy it over
  the corresponding `test-expected/<name>.txt`.
- To add a test: create `tests/<name>/Makefile` (plus venv marker files as appropriate), add a
  `$(eval $(call TEST_RULE, <name>, <goal and vars>))` line to the top-level `Makefile`, and create
  `test-expected/<name>.txt`.
- The top-level Makefile sets `OS := Unknown` and unexports `USE_DOCKER`/`USE_PODMAN` so test
  output is deterministic across platforms.

## Makefile.base architecture

- Runs against the system Python by default (`PYTHON_IMAGES := system`), or against the official
  `python:X.Y` container images when `USE_DOCKER=1` or `USE_PODMAN=1` is set. `VENV_RUN_FN` wraps
  commands in `docker run`/`podman run` in that case.
- Rules are generated by template functions expanded with `$(eval $(call ...))`:
  - `VENV_RULE_FN` creates one venv per image under `build/venv/<image-name>` with a `.build`
    marker file as the make dependency.
  - `VENV_COMMAND_FN` generates a per-image phony target (e.g. `test-python-3-13`) plus the
    aggregate target (e.g. `test`) that depends on it.
- The first image in `PYTHON_IMAGES` is the default image: `cover`, `lint`, `doc`, and `publish`
  run only against it; the remaining images run tests only. A separate `-util` venv holds
  publishing tools (build, twine, simple-git-changelog).
- Because rule bodies pass through `$(call)`/`$(eval)`, `$` escaping depth matters: `$$` defers
  expansion one level, `$$$$` two levels. This is the easiest thing to break when editing.
- Pinned tool versions (`COVERAGE_VERSION`, `PYLINT_VERSION`, `SPHINX_VERSION`,
  `UNITTEST_PARALLEL_VERSION`) are set near the top of `Makefile.base`; bumping them changes the
  dry-run output, so the affected `test-expected/*.txt` files must be updated in the same commit.
